# 협업 운영 규칙

이 문서는 Git, 회의, 로컬 파일과 구현 인수인계를 다루는 저장소 운영 기준입니다.
게임 기획의 최신 기준은 Notion `괴이탐사국 팀 기획서`와 하위 `기획 문서`이며,
README와 이 문서가 기획 내용을 대신 확정하지 않습니다.

---

## 0) TL;DR (3줄)
1) **기획 결정**을 했으면 → Notion 원문과 `15. 미결 안건표`에 반영
2) **구현 변경**을 했으면 → 테스트 결과와 `HANDOFF.md` 현재 상태를 갱신
3) **구조/이동/이름 변경**을 했으면 → README·로컬 허브·관련 링크를 함께 점검

---

## 1) Git 운영 원칙
- `main` = **공유 기준 브랜치**
- 현재는 **직접 커밋/푸시 가능**(브랜치 보호 없음)
- 원칙:
  - 작은 문서 수정/링크 정리/회의 반영: `main` 직커밋 OK
  - 구조 개편/대량 이동/구현 리스크 큰 작업: 브랜치 권장

### 브랜치 네이밍
- `feat/<기능명>` — Unity 기능 구현 (예: `feat/card-battle`, `feat/map-node`)
- `docs/<topic>` — 기획서/문서 작업 (기획서 변경은 이 브랜치 사용)
- `art/<topic>` — 아트/에셋 작업 (스프라이트, UI 이미지, 사운드 등)
- `fix/<topic>` — 버그 수정

### Unity 기능 브랜치 재사용 정책
- 기능은 **기능 단위로 브랜치 분리**해서 구현 → main 병합
- 병합 후 **동일 기능 추가 작업이 생기면 같은 브랜치(`feat/<기능명>`)를 재사용**
  - 새 브랜치를 만들지 말고 기존 브랜치에서 이어서 작업 후 재병합
- 기능 간 의존이 생기는 경우에만 팀 채널에 사전 공유

### PR 정책
- PR은 **필수 아님(선택 도구)**
- PR을 쓰는 경우 포함 권장:
  - 변경 이유(1~3줄)
  - 변경 파일/범위
  - 영향(문서/시스템/빌드)

### 커밋 메시지 컨벤션
- `docs:` 문서 변경
- `feat:` 기능 추가
- `fix:` 버그/오탈자/링크 수정
- `chore:` 구조 정리/설정 변경
- `art:` 아트/에셋 추가 및 변경

예시:
- `docs: 3/15 회의 반영 및 허브 링크 정리`
- `feat: 카드 전투 기본 로직 구현`
- `art: 카드 스프라이트 초안 추가`
- `chore: 문서 폴더 구조화(기획/운영/디자인_UI)`

## 2) 문서와 기록의 역할

- Notion: 최신 게임 기획, 미결 상태, 용어, 디자인 기준과 변경 기록
- 저장소: Unity 구현, 코드 규칙, 구현 인수인계, 회의·일정과 제출 패키지
- Discord: 실시간 논의와 임시 로그
- `기획/`, `기획_통합/`, `디자인_UI/`: 2026-08-01 이전 읽기 전용 아카이브

저장소를 Obsidian Vault로 열어 탐색할 수는 있지만, 로컬 아카이브를 최신 기획으로
수정하지 않습니다. 구조 변경 시 README와 `00_프로젝트_허브.md`를 갱신하고 깨진
상대 링크를 점검합니다.

## 3) 회의 후 10분 루틴(권장)
1) `회의록/` 또는 팀이 정한 회의 기록 위치에 원문 저장
2) 기획 결정은 관련 Notion 페이지와 `15. 미결 안건표`에 반영
3) 구현 액션은 이슈·작업 목록과 필요 시 `HANDOFF.md`에 반영
4) 로컬 파일이 바뀌었으면 관련 링크를 확인하고 작은 단위로 커밋

---

## 4) 충돌 방지(필수)
- 같은 파일 동시 편집 금지(특히 허브/핵심 명세)
- 큰 수정 시작 시 팀 채널에 공유:
  - "지금 `<파일명>` 수정 시작"
- 이동/리네임 후에는 **즉시 링크 점검**

---

## 5) 리뷰/검토 기준(권장)
- 문서 변경은 가능한 한 **작게 쪼개기**(한 번에 읽히게)
- 수치(밸런스 등) 변경은 **근거 1줄 필수**
- 구조 개편/시스템 기준 변경/대량 이동은 최소 1회 팀 확인 권장

## 6) 문서 파일 네이밍 규칙

> 이 섹션은 폴더 분리 이후 번호 체계 혼선을 방지하기 위해 추가됐다. (2026-04-10)

### 배경

초기에는 폴더 없이 번호로 카테고리를 구분했기 때문에 같은 번호를 여러 파일이 공유하는 상황이 발생했다.
현재는 **폴더가 카테고리를 담당**하고, **번호는 폴더 내 읽기 순서만 담당**한다.

### 핵심 원칙

> **번호 = 읽어야 하는 순서**
> 번호가 낮을수록 추상적(개념/구조), 높을수록 구체적(데이터/수치)

1. **번호는 폴더 내 고유값** — 같은 폴더 안에서 같은 번호를 가진 파일이 2개 이상 존재하면 안 된다
2. **번호는 논리적 의존 순서 기준** — "이 문서를 읽으려면 먼저 읽어야 하는 문서"가 더 낮은 번호
3. **새 파일은 끝에 추가** — 기존 번호 사이에 끼워넣지 않는다. 기존 흐름을 깨지 않기 위함
4. **파일 번호 변경 = 구조 개편** — 번호를 바꾸면 README 링크도 반드시 같이 갱신
5. **`00_`은 인덱스/허브 전용** — 폴더의 진입점 역할을 하는 README 또는 허브 문서에만 사용

### 파일명 형식

```
[번호]_[내용_설명].md
```

- 번호: 두 자리 숫자 (`01`, `02`, ... `10`, `11`, ...)
- 구분자: 언더스코어(`_`)
- 내용 설명: 한국어, 단어 사이 언더스코어

예시:
- ✅ `02_전투_시스템_명세.md`
- ✅ `10_동료_스킬_데이터.md`
- ❌ `02_전투시스템명세.md` (언더스코어 없음)
- ❌ `전투_시스템_명세.md` (번호 없음)

### 폴더별 번호 독립

번호는 **폴더마다 독립적으로 시작**한다.
`기획/코어/01_` 과 `기획/시스템/01_` 은 서로 다른 파일이며 충돌이 아니다.

### 새 파일 추가 시 체크리스트

1. [ ] 같은 폴더에 동일 번호 파일이 없는지 확인
2. [ ] 번호가 논리적 순서에 맞는지 확인 (보통 가장 큰 번호 + 1)
3. [ ] 파일 생성 후 해당 폴더의 README 또는 로컬 허브 링크 추가
4. [ ] `00_프로젝트_허브.md` 영향 여부 확인
